Artifact 1 — AI Lab Work

Featured project

Socratic DSA Study Buddy — an AI assistant that refuses to hand over solutions

A chatbot built to help a student practise coding-interview problems without destroying the learning. Instead of giving the answer, it asks guiding questions and offers hints one rung at a time, following a fixed practice protocol: 20 minutes of solo effort first, then hints, then Socratic questions.

The problem

Existing AI assistants hand over full solutions on the first ask. For a student practising problems, that ends the learning the problem was meant to produce — the answer is seen, but the skill is never built. I designed an assistant whose core feature is a refusal: it will not produce a full solution, full code, or a complete walkthrough, no matter how it is asked.

How it was built

  • Design thinking: empathise (my own experience as a DSA student in the practice phase) → define (“How might we help a DSA student practise without the assistant destroying the learning?”) → ideate (six assistant concepts, one chosen) → prototype → test → iterate.
  • Version 1: a chatbot I wrote by hand in HTML/JavaScript to learn how a rule-based bot works from the inside — chat interface, message routing, and a hint ladder implemented in code.
  • Version 2 (live product): the same rules expressed as instructions to a language model on the Mizou platform, so the design applies to any wording of a request and to problems it was not explicitly seeded with.

How it works

  • Effort check first: which problem are you on, and have you spent 20 minutes on it alone?
  • Restatement before help: input, exact output, and a brute-force attempt, in the student’s own words.
  • Hints one rung at a time: pattern → state / data structure → skeleton in words (never code) → edge cases.
  • When a student is stuck, it asks for the smallest failing input and expected vs. actual — then asks a question about that failure instead of correcting it.
  • It closes each solved problem by asking the student for a one-sentence pattern note.

Testing

Five test conversations were run against the finished bot: a normal problem session, a user begging for the full solution (refused, with the reason stated), an off-topic question (redirected once, back to the problem), the unreachable-node edge case (raised as questions, never handed over), and a frustrated “I’m stuck” (answered with the smallest-failing-input protocol). All five behaved as designed, and the same rules were verified to generalise to a problem the bot was not seeded with.
